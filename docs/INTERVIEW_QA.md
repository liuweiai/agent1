# FactoryPilot 面试问题与参考答案

> 适用岗位：Agent 应用开发、Java 后端开发、AI 应用工程、LangChain/LangGraph 工程、MES 数字化开发。
>
> 回答原则：先讲结论，再讲实现，最后讲取舍。不要把演示数据说成真实工厂数据；Redis/Celery、A2A、Neo4j 已落地，但共享数据库 checkpointer、真实 Embedding 和真实工厂数据仍属于后续规划。

## 1. 面试开场模板

### 1.1 30 秒版本

我做了一个面向 MES 场景的生产异常诊断与闭环处置系统 FactoryPilot。它不是普通问答机器人，而是使用 LangGraph 编排一个有状态的长流程：先并行查询质量、告警、维修和 SOP 数据，再用确定性程序计算批次基线、异常窗口、参数相关性和时间重合度，并结合 Neo4j 故障路径与独立厂商 A2A Agent 形成证据。高风险写操作会通过 interrupt 暂停，主管审批后才调用 Action MCP 创建维修工单，最后验证连续批次是否恢复并生成事故报告。系统使用 Redis 分布式锁和 Celery Worker 执行可重试任务，并实现 JWT/RBAC、SSE、审计和 LangSmith 评测。

### 1.2 1 分钟版本

这个项目解决的是生产现场异常定位慢、数据分散和处置缺少闭环的问题。例如用户输入“2 号产线激光打码良率从 98% 降到 91%”，系统不会直接让大模型猜原因，而是先由 Triage 节点识别产线、设备和风险等级，再并行查询 MES 批次质量、设备告警、维修记录和 SOP。之后进入确定性统计分析节点，计算最近 20 个批次的趋势、异常前后均值、打码速度/激光功率/温度与缺陷率的相关性，以及告警和良率下降的时间重合度。RCA Agent 只能引用这些证据 ID 来形成假设。

对于创建维修单等写操作，LangGraph 会用 interrupt 暂停；Spring Boot 网关通过 JWT 和 RBAC 验证主管身份，审批后才恢复图执行。Action MCP 还会再次读取数据库中的审批状态，而不是相信模型传入的参数。整个过程通过 SSE 展示执行时间线，并持久化到 MySQL、LangGraph checkpoint 和审计表。项目的重点是“确定性分析 + Agent 推理 + 安全工具执行”，而不是堆很多 Agent。

### 1.3 3 分钟版本的讲解顺序

1. 业务问题：生产异常数据分散，工程师依赖经验排查，处理过程不可审计。
2. 技术难点：多源数据并行收集、根因分析要有证据、写操作要受控、长流程要能恢复。
3. 核心方案：LangGraph 有状态工作流，确定性统计分析先于 LLM，RAG 提供 SOP 证据，MCP 隔离工具边界。
4. 安全设计：只读 MCP 不暴露任意 SQL，写操作双重校验审批，JWT/RBAC、网关共享密钥、参数白名单、幂等键、审计日志。
5. 工程化：MySQL、Redis/Celery、Milvus、Neo4j、Docker Compose、SSE、失败重试、checkpoint、LangSmith 和离线评测。
6. 结果与反思：80 条离线样例困难场景通过率 92%，保留多设备和空知识结果失败案例；当前仍是合成数据，checkpoint 仍是共享 SQLite，下一步加强真实 embedding、多主机状态存储和统计评测规模。

## 2. 项目定位与架构

### Q1：为什么选择 MES 异常诊断，而不是智能客服？

**参考回答：**

智能客服主要展示知识问答，难以体现我在 MES 实习和 Java 后端方面的能力。生产异常诊断同时包含结构化数据查询、时间序列分析、文档检索、工具调用、人工审批和业务写操作，能完整展示 Agent 从分析到执行的闭环。它也迫使我处理权限、幂等、审计和恢复这些真实工程问题，而不只是优化 Prompt。

### Q2：这个项目真正解决的业务问题是什么？

**参考回答：**

核心解决三个问题：第一，质量、告警、维修和 SOP 分散在不同系统，人工排查成本高；第二，传统大模型容易给出没有证据的原因；第三，诊断与处置脱节，写操作缺少审批、审计和结果验证。FactoryPilot 把多源证据收集、统计分析、根因假设、人工审批、工单执行和恢复验证串成了可追踪的工作流。

### Q3：系统的核心技术架构是什么？

**参考回答：**

前端使用 React、TypeScript、Ant Design 和 ECharts；Spring Boot 网关负责认证、RBAC、SSE 转发和可信身份注入；FastAPI API 把任务投递到 Redis Broker，由 Celery Worker 执行 LangGraph；三个 MCP Server 隔离 MES 查询、知识检索和写操作；MySQL 保存业务状态，Milvus 保存知识向量，Neo4j 提供故障多跳路径，独立厂商 Agent 通过 A2A 协作；SQLite checkpoint 保存图状态，LangSmith负责 Trace 和评测。

### Q4：为什么同时使用 Spring Boot 和 FastAPI？

**参考回答：**

这是按职责和生态拆分。Spring Boot 更适合承接已有 MES 的 Java 业务体系，负责账号、权限、网关和稳定 API；Python 生态在 LangGraph、LangChain、Milvus 和数据分析方面更成熟，所以 Agent 编排放在 FastAPI。两者通过 REST 和 SSE 通信。这样既体现了 Java 后端能力，也避免为了统一语言牺牲 Agent 开发效率。

### Q5：这算微服务架构吗？

**参考回答：**

它是按服务拆分并通过容器部署的应用，但我不会把它包装成完整的 Spring Cloud 微服务体系。当前没有服务注册发现、配置中心、分布式事务或完整服务治理。更准确的说法是“Java 网关 + Python Agent 服务 + 独立 MCP 工具服务”的模块化服务架构。

### Q6：为什么没有使用 Spring Cloud？

**参考回答：**

当前 MVP 服务数量固定，Docker Compose 中可以通过服务名直接寻址，引入注册中心和配置中心的收益有限。项目优先验证 Agent 闭环、安全和评测。若进入多环境、多实例和动态扩容阶段，再引入网关治理、配置中心和服务发现会更合理。

### Q7：为什么加入 Neo4j，怎么避免为了堆技术？

**参考回答：**

MySQL 适合批次和告警等事实查询，Milvus 适合文档语义召回，但“设备型号—部件—故障模式—症状—措施—SOP”是稳定的多跳关系。项目只让 Neo4j 负责这类路径遍历，不替代业务库；查询使用标签、参数化 Cypher、只读 routing 和结果上限，并写审计。RCA 把图谱结果作为候选证据，不能把关系路径直接当成已证明因果。

### Q8：Redis 在项目里具体解决什么问题？

**参考回答：**

Redis 有四个明确职责：作为 Celery Broker/Result Backend；用 `SET NX EX` 获取跨进程 run 锁并用 Lua 校验 owner 后释放；通过 Pub/Sub 唤醒 SSE 读取；缓存 A2A 任务结果以支持幂等 `tasks/get`。MySQL 仍是业务状态和事件的最终事实来源，Redis 丢失不会凭空生成业务状态。当前锁还缺少续租，这是长任务场景的已知改进点。

### Q9：为什么 A2A 没有放在内部 Agent 之间？

**参考回答：**

内部节点共享同一个 LangGraph 状态，直接编排更简单、更可控，所以没有把 Triage、Data、RCA 都包装成 A2A Agent。A2A 只用于独立部署、可被不同团队维护的设备厂商专家服务：主系统先读取 `/.well-known/agent-card.json` 做能力发现，再通过带 Bearer Token 的 JSON-RPC `message/send` 请求诊断，并支持 `tasks/get` 和相同 message id 的幂等返回。

### Q10：这个系统是 Agent，还是普通工作流？

**参考回答：**

它是一个“有边界的 Agent 工作流”。流程拓扑、权限点和失败边界由 LangGraph 明确定义，RCA 节点在受控证据范围内使用模型推理并产生结构化决策，系统还会调用外部工具、根据状态分支、人工中断和恢复。它不是完全自由的 ReAct Agent，而是更适合生产场景的 bounded agent。生产系统中可控性通常比完全自治更重要。

## 3. LangGraph 与 Agent 工作流

### Q11：LangGraph 工作流有哪些节点？

**参考回答：**

主流程是：`triage` 异常分类；并行执行 `mes_data`、`alarm_data`、`maintenance_data` 和 `knowledge_data`；汇合到 `statistical_analysis`；再并行取得 Neo4j 故障路径与 A2A 厂商意见，汇合后执行 `rca`、`plan` 和 `approval`。审批同意后进入 `execute`，拒绝则进入 `reject`；之后执行 `verify` 和 `report`。

### Q12：为什么不是每个节点都包装成 Agent？

**参考回答：**

确定性任务不需要 LLM。例如固定参数校验、数据库查询、均值和相关性计算、审批校验都应该用普通函数完成。只在需要综合证据、产生根因假设的 RCA 节点使用模型。这样减少 Token 成本、降低延迟和随机性，也更容易测试和审计。

### Q13：四个角色和十几个节点是什么关系？

**参考回答：**

角色是职责抽象，节点是实际工作流步骤。TriageAgent 对应分类节点；DataAgent 的职责被拆成多个并行采集节点；RCAAgent 对应统计分析后的根因推理；ActionAgent 覆盖计划、审批后执行和验证。角色不等于一个独立进程，也不需要每个角色使用一个模型。

### Q14：并行数据收集是怎么实现的？

**参考回答：**

在 LangGraph 中，`triage` 同时连接到四个采集节点，四个节点完成后再汇聚到统计分析节点。证据字段使用 reducer 进行列表合并，避免并行分支互相覆盖。这样可以降低总等待时间，同时保持结果合并规则明确。

### Q15：如何避免并行节点写状态时发生覆盖？

**参考回答：**

共享状态中需要累加的 `evidence` 字段使用 `Annotated[list, operator.add]` 定义 reducer，每个节点只返回自己的增量。对于不适合合并的标量字段，节点要保持单一写入责任。生产中还应为每类结果使用独立字段，减少模糊的最后写入覆盖。

### Q16：人工审批如何实现？

**参考回答：**

`approval` 节点调用 LangGraph 的 `interrupt`，把风险等级、计划和运行 ID 作为中断数据返回。图状态通过 checkpoint 保存，接口状态更新为 `awaiting_approval`。主管在前端审批后，网关验证 JWT 和角色，把真实登录用户名作为审批人发送给 Agent 服务，再通过 `Command(resume=...)` 使用相同 `thread_id` 恢复执行。

### Q17：为什么不能只在前端做审批按钮？

**参考回答：**

前端按钮只是交互，不是安全边界，攻击者可以直接调用接口。项目中网关会做 RBAC，Agent 服务要求请求经过可信网关，Action MCP 在执行前还会根据 `run_id` 读取数据库里的实际审批状态。因此即使模型或客户端伪造 `approved=true`，写工具也不应该直接执行。

### Q18：服务重启后任务如何继续？

**参考回答：**

LangGraph 使用 SQLite checkpointer，并以 `run_id` 作为 `thread_id`，所以图状态和中断位置可以跨进程保留。业务运行状态同时保存在 MySQL。重启后，审批接口使用原 `run_id` 恢复对应线程。当前版本没有自动扫描并恢复所有“运行中”任务，生产化会增加启动恢复器和持久化队列。

### Q19：如何防止图无限循环？

**参考回答：**

图调用设置了 `recursion_limit=30`，工具调用也设置最大重试次数，Action MCP 限制同类写操作的执行次数。当前拓扑本身没有自由循环，验证失败会生成结论而不是无限回到计划节点。未来若加入自动重规划，会在状态中维护 attempt，并给条件边设置明确上限。

### Q20：为什么使用显式图，而不是一个 ReAct Agent 自己决定？

**参考回答：**

生产处置需要可预测的审批点、权限边界和审计顺序。自由 ReAct 可能跳过验证、重复调用工具或选择危险动作。显式图能保证“先取证、再分析、再审批、后执行”，模型只在局部做推理。代价是扩展新流程时需要修改图，但换来了稳定性和可测试性。

### Q21：AgentState 中保存哪些信息？

**参考回答：**

主要包括 run ID、用户问题、产线和设备标识、异常类型、严重度、多源证据、统计分析结果、根因假设、处置计划、审批结果、工具执行结果、验证结果、报告、当前步骤和错误信息。State 是节点之间的数据契约，尽量使用结构化 Pydantic 模型，而不是把整个对话文本不断拼接。

### Q22：如何处理同一任务被重复启动？

**参考回答：**

服务层先用进程内集合快速防重，再用 Redis `SET NX EX` 获取跨进程 run lease；释放锁时执行 compare-and-delete Lua，避免误释放其他 Worker 的锁。Celery task id 由 run id 和 approval id 确定，业务动作还有数据库幂等键和唯一约束，审批接口则用状态机阻止重复审批。锁 TTL 目前不自动续租，因此任务硬超时必须小于锁 TTL。

### Q23：为什么使用 Celery，而不是 FastAPI BackgroundTasks？

**参考回答：**

本地 profile 仍可使用 BackgroundTasks 方便开发，但 Docker 完整模式使用 Celery + Redis。诊断和审批恢复由独立 Worker 消费，配置 late ack、`reject_on_worker_lost`、prefetch=1、有限指数退避和软/硬超时。队列解决进程隔离和可重试调度，业务幂等仍由 run 状态、审批记录和动作唯一键保证；不能把“消息可重试”等同于“副作用天然 exactly-once”。

## 4. 确定性生产数据分析

### Q24：为什么要在 LLM 前增加确定性分析节点？

**参考回答：**

LLM 擅长综合和解释，但不应该负责精确统计计算。系统先用程序计算均值、变化幅度、相关性和时间重合，再把结果作为证据交给 RCA Agent。这样可以复现、单元测试，并能向面试官或现场工程师解释每个结论来自哪一条数据，而不是让模型凭语言模式猜测。

### Q25：异常前后均值是怎么算的？

**参考回答：**

当前实现读取最近 20 个批次，以 97% 良率阈值区分正常基线和异常批次，分别计算均值，再计算百分点差值和相对降幅。为了避免少量数据误判，统计证据充足要求总批次数至少 8、基线至少 3、异常至少 2。生产版本更适合按事件时间划分异常前窗口和异常窗口，并使用滚动基线或同产品配方基线。

### Q26：相关性是怎么计算的？

**参考回答：**

将每个批次的打码速度、激光功率和设备温度分别与缺陷率做 Pearson 相关系数计算。系数越接近 1 表示正相关越强，越接近 -1 表示负相关越强。系统把数值、样本数和变量名称写入统计证据，由 RCA Agent解释，但不会把相关性直接说成因果关系。

### Q27：Pearson 相关性有什么局限？

**参考回答：**

它只反映线性关系，对异常值敏感，也无法排除产品型号、班次、耗材批次等混杂因素。样本量小时结果不稳定。后续可增加 Spearman 相关、分层分析、置信区间、滞后相关和回归模型，并按工艺配方控制变量。

### Q28：如何判断告警与良率下降是否重合？

**参考回答：**

先确定异常批次的时间范围，再查询该设备附近的告警，当前使用异常窗口前后约 6 小时的容差判断时间重合，并统计告警级别和类型。这个结果是辅助证据，不代表告警一定导致质量下降。生产中会统一设备时间源，并考虑数据采集延迟和告警持续时间。

### Q29：为什么取最近 20 个批次？

**参考回答：**

20 是演示数据下兼顾趋势可读性和查询成本的窗口，不是通用最佳值。真实项目会根据节拍、产品切换频率和工艺稳定周期设置时间窗口，甚至针对不同设备动态配置。

### Q30：如何验证处置是否有效？

**参考回答：**

执行后重新查询质量数据，要求连续 3 个批次达到恢复阈值才判定恢复，避免单批偶然回升。当前演示验证数据为 96.8%、97.4%、97.9%，因此只有连续两个批次达标，状态是“继续观察”而不是虚假宣称已恢复。

### Q31：如果数据不足怎么办？

**参考回答：**

统计节点会给出 evidence sufficient 标记。数据不足时降低置信度，并在计划中优先建议补采数据、检查传感器或人工复核，不应生成确定性根因。高风险动作仍然需要审批，不能因为缺数据而绕过安全控制。

### Q32：当前基线算法有什么需要改进的地方？

**参考回答：**

目前按良率阈值分类可能产生选择偏差，因为基线和异常是通过结果变量本身划分的。更严谨的方法是以异常发生时间为界，取之前稳定窗口作为基线，之后作为异常窗口，并按产品、配方和设备状态分层。我会把这是 MVP 的限制明确告诉面试官。

### Q33：为什么不用大模型直接写 Python 做分析？

**参考回答：**

动态生成代码会带来执行安全、依赖、超时和结果不可重复问题。项目把统计逻辑写成经过测试的固定函数，模型只读取结果。如果未来需要沙箱分析，也应采用受限数据集、禁网容器、资源配额和代码审计，而不是直接在业务服务执行模型代码。

## 5. RCA、LLM 与结构化输出

### Q34：项目使用了什么模型？

**参考回答：**

默认 Demo 模式使用确定性 RCA 引擎，保证没有外部 Key 时也能演示完整闭环。配置为 LLM 模式后，通过 OpenAI 兼容接口调用 DeepSeek 或 OpenAI 模型，温度设置为 0，并要求 Pydantic 结构化输出。模型只是 RCA 节点的一部分，不负责权限和直接数据库执行。

### Q35：DeepSeek API Key 应该如何配置？

**参考回答：**

在项目根目录 `.env` 中设置 LLM 模式、兼容接口地址、模型名和 Key，例如 `AGENT_MODE=llm`、DeepSeek base URL、`deepseek-chat` 以及对应 API Key。真实 Key 不提交 Git，`.env` 已被忽略，仓库只保留 `.env.example`。修改后需要重新创建 Agent 容器，让环境变量生效。

### Q36：如何防止模型输出非法 JSON？

**参考回答：**

RCA 输出定义为 Pydantic Schema，限制根因列表、置信度、证据 ID、风险和说明字段。调用失败或解析失败会记录错误，并按受控策略重试，最终回退到确定性引擎。模型输出永远要经过 Schema 校验，不能直接作为工具参数执行。

### Q37：如何减少模型幻觉？

**参考回答：**

一是先提供结构化统计证据；二是要求每个假设引用 evidence ID；三是服务端过滤不存在的 evidence ID；四是没有有效引用时把置信度上限压到 0.35；五是写操作必须经过固定计划校验和人工审批。这样即使语言表述听起来合理，也必须能映射到实际证据。

### Q38：模型不可用时系统怎么办？

**参考回答：**

当前采取“分析能力 fail-open、写操作 fail-closed”的策略。LLM 超时或输出异常时，RCA 回退到确定性规则，并在状态中标记 degraded；但任何高风险写操作仍必须经过审批和 Action MCP 校验。这样能继续提供基础诊断，又不会因为降级而放松执行安全。

### Q39：为什么温度设置为 0 仍然不能保证完全一致？

**参考回答：**

服务端实现、模型版本、并发和浮点计算仍可能带来差异，温度 0 只是降低采样随机性。真正的稳定性来自结构化约束、固定证据、确定性节点、回归评测和失败降级，而不是只依赖 temperature。

### Q40：根因分析是如何排序的？

**参考回答：**

确定性引擎会综合质量变化、参数相关性、告警重合、维修历史和 SOP 支持度形成候选；LLM 模式则要求输出有序假设及置信度。服务端验证引用后再展示。当前置信度是工程评分，不是严格概率，生产版本需要用标注案例做校准。

### Q41：处置计划是模型自由生成的吗？

**参考回答：**

不是完全自由。当前演示场景使用受控动作类型、参数范围和风险规则，模型可以辅助生成说明，但真正可执行工具只接受白名单动作。激光设备场景的部分计划仍是模板化的，这是为了安全和演示稳定；未来会将 SOP 转换为版本化的动作策略和约束 Schema。

## 6. RAG 与 Milvus

### Q42：知识库中保存什么内容？

**参考回答：**

保存设备手册、维修指南和异常处置 SOP。每个段落包含文档 ID、标题、章节、正文、版本和元数据。检索结果会返回来源和段落引用，RCA 只使用可验证的文档片段。

### Q43：RAG 的完整流程是什么？

**参考回答：**

文档先按段落切分并生成向量，写入 Milvus；查询时同时计算向量相似度和词法关键词得分，先召回候选，再用 `0.65 × dense + 0.35 × lexical` 重新排序，返回 Top-K 文档。结果进入证据列表并保留文档、章节、版本和分数，最终报告展示引用。

### Q44：为什么使用混合检索？

**参考回答：**

设备代码、告警码和工艺参数往往是精确关键词，纯向量检索可能忽略；而用户自然语言与手册表述不完全一致，纯关键词召回也不足。混合检索能兼顾语义相似和精确术语。

### Q45：当前 embedding 是什么？有什么限制？

**参考回答：**

为了离线可运行，当前使用 128 维确定性 HashEmbedding。它便于测试和复现，但语义能力有限，不能代表生产级中文向量效果。生产版本应替换为 BGE-M3、bge-large-zh 或受控的云 embedding，并重新构建集合和评测 Recall@K。

### Q46：Milvus 中使用什么相似度？

**参考回答：**

使用 COSINE 相似度。查询时先取大于最终 Top-K 的候选，再结合词法得分进行二次排序。索引参数和候选规模应通过离线数据集调优，而不是凭经验固定。

### Q47：RAG 如何提供“有据可依”的答案？

**参考回答：**

每条知识证据都有稳定 ID，并保存标题、章节、正文和版本；RCA 输出只能引用存在的 ID；报告展示引用来源；评测检查输出中的引用是否真实存在并支持结论。当前离线有据可依率较高，但仍需要更难的冲突文档和过期版本案例。

### Q48：Milvus 不可用时怎么办？

**参考回答：**

配置允许在演示环境使用词法检索降级，但 Docker 完整模式默认关闭静默 fail-open，以便及时暴露基础设施问题。无论如何都要记录 degraded 状态，不能把降级结果伪装成完整向量检索。

### Q49：如何处理文档版本冲突？

**参考回答：**

当前元数据保留版本，但冲突消解仍需要加强。生产方案会给文档增加生效时间、设备型号、工艺版本和是否作废字段，默认过滤过期文档；如果两个有效来源冲突，RCA 应显式输出冲突并请求人工确认，而不是选择一个看起来更像答案的片段。

### Q50：为什么不直接把所有文档放进上下文？

**参考回答：**

全量上下文成本高、噪声大、超过模型窗口后还会截断。检索可以缩小到与设备、异常和工艺相关的段落，并保留来源。Top-K 也不是越大越好，需要在召回率和上下文噪声之间平衡。

## 7. MCP、工具调用与安全

### Q51：为什么把工具拆成三个 MCP Server？

**参考回答：**

按照权限和故障域拆分：`mes-mcp` 只读生产数据，`knowledge-mcp` 只做知识检索，`action-mcp` 执行业务写操作。这样可以分别配置网络权限、超时、审计和部署策略，尤其能把高风险写能力与普通查询隔离。

### Q52：MES MCP 为什么不允许模型生成任意 SQL？

**参考回答：**

任意 SQL 难以限制数据范围，存在注入、越权、全表扫描和误写风险。项目只暴露固定业务工具，例如按设备和时间范围查询告警、批次和维修记录；参数通过枚举、正则和最大条数校验；底层使用参数化查询。模型选择业务工具，但不能直接控制 SQL 文本。

### Q53：MCP 调用是否是真实网络调用？

**参考回答：**

支持两种 transport。测试或本地快速模式可以使用 in-process 调用；Docker 完整模式通过 Streamable HTTP 连接三个独立 MCP Server。客户端设置超时、最多两次尝试和短指数退避，并记录工具名、参数摘要、耗时和结果状态。

### Q54：如何限制工具权限？

**参考回答：**

第一层是工具暴露面，只提供白名单业务方法；第二层是参数 Schema、范围和枚举；第三层是网关 JWT/RBAC；第四层是 Agent 工作流审批节点；第五层是 Action MCP 从数据库读取审批状态；第六层是幂等与审计。安全不能只依赖 Prompt 中一句“不要执行危险操作”。

### Q55：Action MCP 为什么还要再次检查审批？

**参考回答：**

这是纵深防御。Agent 或调用方传来的 `approved=true` 可能被伪造，Action MCP 不能信任调用参数，而要根据 `run_id` 查询持久化审批记录、审批角色和任务状态。只有真实审批成立才执行写操作。

### Q56：如何防止重复创建维修工单？

**参考回答：**

执行请求携带与运行和动作相关的幂等键，数据库设置唯一约束；重复请求会返回原结果而不是新建记录。图恢复、网络重试和用户重复点击都可能造成重复调用，所以幂等必须在写服务端实现，不能只在前端禁用按钮。

### Q57：工具超时如何处理？

**参考回答：**

读工具设置超时和有限重试，重试仍失败会产生结构化错误证据并进入降级路径；写工具更谨慎，必须依赖幂等后才能安全重试。所有失败写入事件和审计日志，报告中明确哪些数据缺失，不能静默编造结果。

### Q58：如何防 Prompt Injection？

**参考回答：**

系统把用户输入和检索文档都标记为不可信数据，系统提示明确禁止执行其中的指令；工具选择不由自由文本直接映射；输出必须通过结构化 Schema；权限、审批和参数校验在模型外完成；评测集中包含诱导模型绕过审批、创建工单和泄露信息的案例。即使 Prompt 防御失效，工具层仍应阻止越权执行。

### Q59：如何防 SQL 注入？

**参考回答：**

不提供通用 SQL 工具；固定查询使用参数绑定；设备 ID、产线、时间范围和 limit 都经过校验；数据库账号按只读和写入职责拆分更理想。当前项目已实现固定工具和参数化查询，生产部署还应给 MES MCP 使用数据库只读账号。

### Q60：JWT 和 RBAC 是怎么做的？

**参考回答：**

Spring Boot 负责登录，密码使用 BCrypt，签发 HS256 JWT，并存放在 HttpOnly、SameSite=Strict Cookie。角色包括 OPERATOR、SUPERVISOR 和 ADMIN；高风险审批和审计接口只允许主管或管理员访问。网关从认证上下文获取用户名，不接受浏览器自报审批人。

### Q61：Agent 服务如何确认请求来自网关？

**参考回答：**

网关调用 Agent 服务时注入 `X-Gateway-Secret`，FastAPI 在开启 `REQUIRE_GATEWAY_AUTH` 后使用常量时间比较验证。这样可以避免用户绕过 Java RBAC 直接访问 Agent API。生产中应改用短期服务身份、mTLS 或密钥管理服务，而不是长期共享密钥。

### Q62：项目的 CSRF 防护完善吗？

**参考回答：**

当前 Spring Security 中关闭了 CSRF，主要依赖 SameSite=Strict Cookie 和本地部署边界，作为 MVP 还不够完整。如果跨站场景、反向代理或第三方集成增加，生产版本应启用 CSRF Token 或采用 BFF 的双重提交策略，并严格配置 CORS、Secure Cookie 和受信 Origin。

### Q63：审计日志记录什么？

**参考回答：**

记录运行 ID、操作者、角色、工具名、动作、参数摘要、审批结果、执行状态、耗时、错误和时间。敏感字段应脱敏。审计日志与普通应用日志分开考虑，生产中应追加写、限制修改权限并设置保留策略。

### Q64：默认密钥可以直接用于生产吗？

**参考回答：**

不可以。仓库里的默认 JWT Secret 和网关共享密钥只为本地演示，`.env.example` 也明确提示更换。生产环境应从 Secret Manager 或部署平台注入，并定期轮换，不能写入 Git 或镜像。

## 8. 数据库、接口与前端

### Q65：为什么业务状态和 LangGraph checkpoint 分开保存？

**参考回答：**

两者职责不同。checkpoint 保存图内部状态、节点位置和 interrupt 恢复信息；MySQL 保存面向业务查询的运行摘要、审批、工单、事件和审计。前端不应该解析 LangGraph 内部 checkpoint，业务表也不适合代替图执行状态。

### Q66：主要数据库表有哪些？

**参考回答：**

领域表包含设备、告警、生产批次、质量检测、工艺参数、维修记录、知识文档和产线控制；运行表包含诊断任务、执行事件、审批信息、工具审计和维修工单。表设计围绕“证据来源”和“闭环状态”展开。

### Q67：为什么本地端口和容器端口不一样？

**参考回答：**

Agent 容器内监听 8000，宿主机映射到 8001；MySQL 容器内 3306，宿主机映射到 3307；Milvus 容器内 19530，宿主机映射到 19531。容器之间使用服务名和容器端口，宿主机调试使用映射端口。这个区别也是之前本地启动问题的来源之一。

### Q68：前端为什么使用 SSE，而不是 WebSocket？

**参考回答：**

执行时间线主要是服务端单向推送，SSE 基于 HTTP，断线重连和代理配置更简单。客户端通过事件 ID 和 after cursor 续传，服务端还发送 heartbeat 和 done 事件。审批、启动等客户端到服务端操作仍使用普通 REST，因此不需要 WebSocket 的双向长连接。

### Q69：SSE 如何避免丢事件？

**参考回答：**

事件先持久化到数据库并带单调 ID，Redis Pub/Sub 只负责低延迟唤醒；客户端记录最后收到的 ID，重连时使用 after 参数继续读取，服务端周期性发送心跳。因此 Redis 短暂断线或浏览器重连后仍能从 MySQL 补历史事件。

### Q70：前端为什么不做成聊天框？

**参考回答：**

异常处置的重点是任务状态、证据、风险、审批和执行步骤，而不是多轮闲聊。因此界面采用控制台：最近任务、指标卡、执行时间线、统计图、证据引用、审批面板和审计日志。这样更接近生产运维系统，也更能展示 Agent 的可解释工作流。

### Q71：如何避免前端直接访问受保护的 Agent 接口？

**参考回答：**

Docker 前端通过 Nginx 把 `/api` 代理到 Spring Boot 网关，浏览器只与网关交互。网关完成认证和授权后再调用 Agent 服务。开发模式若直接访问 Agent 端口会收到 401，这是预期安全行为。

### Q72：模拟数据是如何生成的？

**参考回答：**

使用固定随机种子生成 10 台设备、1000 级别告警、500 个生产批次、质量与工艺参数、100 条维修记录和 30 份文档，并额外插入与演示异常强相关的近期数据。固定种子保证测试可复现。所有数据都是合成数据，不包含实习公司的真实信息。

## 9. 评测、LangSmith 与可观测性

### Q73：项目如何做评测？

**参考回答：**

离线评测集共 80 条：30 条意图分类、25 条检索、25 条困难和安全场景。指标包括意图准确率、Recall@4、有据可依率、工具选择准确率、完整任务成功率、高风险违规率和 P95 延迟。LangSmith用于上传数据集、记录 Trace 和运行在线/离线实验。

### Q74：当前评测结果是多少？

**参考回答：**

本地回归中，意图分类和 Recall@4 为 100%，困难场景通过率 92%，有据可依率和工具选择率为 100%，完整任务成功率 75%，高风险违规率 0%，P95 约 530ms。LangSmith 托管的 55 条样例中，引用率约 96.36%、Recall 约 92%。这些是合成数据上的结果，不能等同生产准确率。

### Q75：为什么有些指标是 100%，会不会数据太简单？

**参考回答：**

是的，意图和基础检索集相对规则化，所以 100% 不能说明泛化能力。我专门增加了信息不足、证据冲突、空结果、超时、非法 JSON、Prompt Injection、越权、重复审批、多设备异常等困难案例，并保留失败样例。下一步还需要真实人工标注、同义改写和不同时间分布的数据。

### Q76：当前有哪些失败案例？

**参考回答：**

困难集中在多台设备同时异常时的范围拆分，以及知识 MCP 返回空结果时对引用降级的显式表达。它们说明当前 state 主要围绕单设备设计，空证据情况下的报告模板也需要更严格。保留失败案例比展示全 100% 更可信，也能指导下一个版本。

### Q77：完整任务成功率为什么只有 75%？

**参考回答：**

完整任务要求分类、数据获取、根因引用、审批、执行、验证和报告全部满足条件，比单项指标严格。部分失败来自故意注入的超时、空结果或冲突证据。项目更关注系统是否安全降级，而不是强行把每个异常都标成成功。

### Q78：DeepSeek + RAG 和 + Rerank 对比能得出什么结论？

**参考回答：**

当前每个版本只有 3 条样例，样本太小，而且“完整成功”可能包含规则降级，因此不能宣称某个版本显著更好。现有结果只能验证评测链路和 Token/延迟采集可用。正式对比至少需要几十到上百条固定数据、重复运行、区分模型直出与降级成功，并报告置信区间。

### Q79：LangSmith 为什么可能看不到 Trace？

**参考回答：**

常见原因有：`LANGSMITH_TRACING` 未开启、API Key 或区域 endpoint 不匹配、容器没有重新创建、项目名看错、只刷新页面但没有真正执行一次 Agent 任务，或者网络无法访问 LangSmith。排查时先查看容器环境变量和 Agent 日志，再执行一次诊断，最后按 `LANGSMITH_PROJECT` 查找。

### Q80：如何统计 Token 成本？

**参考回答：**

从模型回调或 LangSmith Trace 中读取 prompt tokens、completion tokens、总耗时和模型名，按照配置的单价计算成本，并按 run ID 聚合。Demo 确定性模式没有真实模型 Token，不应该伪造成本。

### Q81：可观测性包括哪些层次？

**参考回答：**

业务层有任务状态、审批、工单和事故报告；工作流层有每个节点的开始、完成、耗时和错误；工具层有 MCP 调用审计、重试和结果；模型层有 LangSmith Trace、Token 和延迟；基础设施层有容器健康检查和结构化日志。面试时我会重点展示一次 run ID 如何贯穿这些层次。

### Q82：怎样保证评测可复现？

**参考回答：**

固定合成数据随机种子、固定数据集版本和 Prompt 版本；确定性节点使用相同算法；模型温度为 0；报告记录模型名、配置和时间。外部模型仍可能变化，因此要保留原始输入、输出和 Trace，并用多次运行统计波动。

## 10. 性能、可靠性与生产化追问

### Q83：系统当前的主要性能瓶颈是什么？

**参考回答：**

LLM 调用通常是最大延迟，其次是 Milvus 检索和多次 MCP 网络调用。项目通过四路并行采集降低等待时间，通过固定 Top-K 控制上下文，通过超时和降级避免长时间阻塞。多实例生产环境还要处理数据库连接池、SSE 连接数和任务队列吞吐。

### Q84：如何优化响应时间？

**参考回答：**

先用 Trace 分解每个节点耗时，再针对瓶颈优化：并行独立数据源、缓存稳定的 SOP 结果、批量数据库查询、缩小模型上下文、选择更快模型、对非关键结果延迟加载。不能为了速度取消证据检查或审批。

### Q85：如果同时有 100 个诊断任务会怎样？

**参考回答：**

当前 Docker 模式会把任务交给 2 并发 Celery Worker，Redis 提供 Broker、分布式 run 锁和事件通知，因此不会把 100 个诊断都压在 FastAPI 进程里。但它仍不是无限扩展：LLM/MCP/数据库连接池有吞吐上限，SQLite checkpoint 只适合同一主机共享卷，Redis 锁还需要续租。多主机部署应改用数据库型 checkpointer、独立 Worker autoscaling、限流和死信监控。

### Q86：数据库和 MCP 都失败时如何降级？

**参考回答：**

结构化数据不可用时，不应继续给出高置信根因。系统会记录数据源失败、降低置信度，给出人工检查和补采建议；写操作默认不执行。知识检索单独失败时可以保留统计诊断，但报告要明确“缺少 SOP 佐证”。

### Q87：为什么写操作要 fail-closed？

**参考回答：**

创建工单、调整任务或停线会影响真实生产。如果审批服务、身份验证或状态读取失败，系统无法证明操作被授权，因此必须拒绝执行。分析失败可以安全降级，执行授权失败不能默认放行。

### Q88：如何设计灾难恢复？

**参考回答：**

业务数据和 checkpoint 定期备份；每个外部动作有幂等键和可查询结果；任务状态机能够识别“已请求但响应丢失”的不确定状态；恢复器按 run ID 检查最后已提交事件，再决定重试或人工介入。不能简单从头重跑整个图，否则可能重复写操作。

### Q89：如何保证时间数据可靠？

**参考回答：**

所有服务使用统一时区或 UTC 存储，设备、MES 和数据库通过 NTP 校时；事件携带采集时间和入库时间；时间窗口查询明确边界。当前演示使用统一生成时间，生产中还要处理设备离线缓存和迟到事件。

### Q90：如果需要多租户怎么办？

**参考回答：**

用户身份中加入 tenant ID，网关把租户上下文可信传递到下游；所有业务表和工具查询强制带租户条件；Milvus 按 partition、collection 或元数据过滤隔离；审计和密钥也按租户管理。不能依赖模型记得加 tenant 条件。

## 11. 设计取舍与压力面问题

### Q91：你认为项目最有价值的技术点是什么？

**参考回答：**

不是 LangGraph 或 MCP 的数量，而是把“确定性程序分析”和“模型推理”分开：程序负责可复现的指标和安全边界，模型负责综合非结构化证据。再通过审批、幂等、审计和验证把诊断变成闭环。这是从 Demo 型 Agent 走向业务系统的关键。

### Q92：项目中最难的问题是什么？

**参考回答：**

最难的是跨服务的一致性：LangGraph 处于暂停状态、MySQL 记录等待审批、前端显示正确状态、审批后 Action MCP 又能确认授权，几者必须围绕同一个 run ID 对齐。为此我把 checkpoint、业务状态、事件、审批和幂等动作拆开持久化，并让服务端身份覆盖客户端输入。

### Q93：如果重新做一次，你会先改什么？

**参考回答：**

我会先把运行状态机和事件协议设计得更严格，再扩展 Agent 能力；同时把统计窗口从阈值分组改为基于异常发生时间的滚动基线，并用真实中文 embedding 替换 HashEmbedding。这样能同时提高工程可靠性和诊断可信度。

### Q94：这个项目是否过度设计？

**参考回答：**

如果只是做一次性问答，Spring Boot、MCP、Neo4j 和 A2A 都会显得重。但目标是生产异常受控闭环：Neo4j 只处理稳定多跳故障路径，A2A 只连接独立厂商 Agent，内部节点仍由 LangGraph 编排；Redis/Celery 只处理跨进程协调。没有加入 Kubernetes、十几个 Agent 或图谱替代业务库，是为了控制复杂度。

### Q95：哪些部分是你独立完成的？

**参考回答：**

应根据自己的真实过程回答。建议按模块说明：需求拆解与架构、数据库与模拟数据、LangGraph 图、MCP 工具、安全审批、React 控制台、Docker 和评测分别做了什么；如果使用过 AI 编程工具，要如实说明自己负责方案选择、代码审查、联调、测试和问题定位，不要声称每一行都手写。

### Q96：使用 AI 辅助开发会不会说明能力不足？

**参考回答：**

AI 是开发工具，关键是我能否定义边界、验证实现并解释取舍。例如我能指出当前 SQLite checkpoint、Redis 锁续租、HashEmbedding、CSRF 和评测样本量的限制，并能通过日志、审计和测试定位问题。面试中不回避使用工具，但要证明自己理解最终系统并对结果负责。

### Q97：如果面试官说“这只是套框架”，怎么回答？

**参考回答：**

我会展示框架之外的工程决策：为什么统计计算不交给模型、为什么不开放任意 SQL、Action MCP 为什么二次验证审批、如何用 run ID 贯穿 checkpoint/审计/SSE、如何处理重复执行和空证据、评测中为什么保留失败案例。这些才是应用工程能力，框架只是实现手段。

### Q98：如果根因分析错了，谁负责？

**参考回答：**

系统定位是辅助决策，不把模型输出当最终事实。报告展示证据、置信度和数据缺口，高风险处置由有权限的人审批；执行动作受白名单限制；处理后还要验证。生产上线还需要明确责任制度、模型版本、审批记录和回滚流程。

### Q99：如何向非技术主管说明这个系统？

**参考回答：**

它像一个会自动取证的生产异常助手：把原本要在多个系统里查的数据集中起来，先用程序算出异常变化，再参考手册给出有来源的建议。它不会自己停线或改任务，重要操作必须由主管确认，处理后还会继续观察是否恢复，并留下完整记录。

### Q100：这个项目下一阶段的优先级是什么？

**参考回答：**

第一，用真实中文 embedding 和更严格的文档版本治理提高检索质量；第二，扩展时间窗口和多设备统计分析；第三，把 SQLite checkpoint 升级为数据库型共享存储并为 Redis lease 增加续租；第四，扩大人工标注评测集并区分模型成功与规则降级；第五，把当前演示厂商 A2A 替换为真实服务并补异步任务取消。Kubernetes 只有在部署规模确实需要时再加入。

## 12. 现场演示时可能被追问的故障

### Q101：页面提示 Unauthorized，怎么排查？

**参考回答：**

先确认访问的是 Docker 前端 `http://localhost:3000`，而不是绕过网关直连开发端口；然后使用演示账号登录，检查浏览器是否收到 HttpOnly Cookie；再查看 gateway 和 agent-service 日志。若 `/api/runs` 直接到 Agent 端口，401 是安全策略正常工作，不是服务未启动。

### Q102：修改 `.env` 后为什么没有生效？

**参考回答：**

Docker Compose 在创建容器时注入环境变量，单纯刷新浏览器不会改变容器环境。需要在项目根目录运行 `docker compose up -d --force-recreate agent-service`，涉及其他服务时重建对应容器，再通过 `docker compose logs` 和容器环境检查确认。

### Q103：LangSmith 配好 Key 后下一步做什么？

**参考回答：**

确认 tracing 为 true、endpoint 与账号区域匹配、project 名正确，重建 Agent 容器，然后从前端完整执行一次诊断。只有真正执行 LangGraph/LLM 调用才会产生 Trace。最后在 LangSmith 的对应项目中按时间和 run ID 检查。

### Q104：为什么本地开发页和 Docker 页表现不同？

**参考回答：**

开发页可能配置为直连 Agent，而完整 Docker 链路要求前端经 Nginx 到 Spring Boot 网关，再到 Agent。权限开启后，直连请求缺少 JWT 或网关共享密钥，会返回 401。部署时要统一 API base URL，避免同时打开旧开发服务器造成混淆。

### Q105：如何证明不是写死的演示？

**参考回答：**

现场可以切换不同异常问题，展示 MySQL 中真实查询结果、MCP 审计、统计图数值、LangGraph interrupt、不同角色审批结果、幂等重复执行、Milvus 引用和 LangSmith Trace。同时主动说明当前激光打码案例含有固定模拟数据和模板动作，边界说清楚比假装全动态更可信。

## 13. 面试前自查清单

- 能在白板上画出：浏览器 → Spring Boot → FastAPI/LangGraph → MCP/MySQL/Milvus。
- 能不看代码说出全部核心节点和审批恢复流程。
- 能解释一次 run ID 如何关联运行状态、checkpoint、SSE、审批、审计和工单。
- 能手算均值差、解释 Pearson 相关，但明确相关不等于因果。
- 能说明为什么不用任意 SQL、为什么 Action MCP 二次检查审批。
- 能说出 HashEmbedding、SQLite checkpoint、Redis 锁 TTL、Celery at-least-once 语义和 CSRF 的限制。
- 能解释 100% 指标为什么不能代表生产效果，并说出两个保留的失败案例。
- 能现场启动项目、登录、发起诊断、审批、查看审计和 LangSmith Trace。
- 能明确区分已实现、演示实现和未来规划。
- 准备一个真实的故障排查故事，例如 401、容器端口、环境变量未重建或 GitHub 网络失败。
